# 交付前 QA

逐项检查并在内部记录结果：

- 原始文件夹的文件数量、名称、哈希是否保持不变；
- 是否从内置案由表提出候选，并按四级、三级、二级、一级顺序选择最具体且有依据的案由；
- `cause_of_action_review` 是否记录层级、依据、排除项和用户确认状态；
- 案件根文件夹是否严格采用 `序号-原告简称VS被告简称-确认案由`；
- 项目文件夹、Word 文件及标题、HTML 文件及页面标题是否使用同一个确认案由；
- 是否记录用户选择的目录模式；默认模式是否只有 `001` 至 `005` 五个材料目录，自定义模式是否严格等于用户确认的目录；
- 默认模式的 `002 基础资料` 是否按材料内容建立二级目录，且没有按文件格式或一份文件一个文件夹地分类；
- 原文件总数与已归档、重复、失败、未处理数量能否对平；
- 是否记录并遵守用户选择的处理深度；快速归档是否避免了不必要的逐页阅读；
- 案件脉络或报告模式的关键材料是否全部核对，关键事实是否只引用已核对材料；
- 延后专项核对和无法读取的材料是否明确披露；用户选择全量复核时，`reading_coverage` 是否覆盖全部材料和阅读单元；
- `fact_inventory` 中每项事实是否有来源材料和原文定位；是否避免用单文件摘要代替事实提取；
- 事实处置率是否为 100%；每项事实是否且仅进入报告、时间轴、背景或待确认清单之一；
- 所有具有法律相关性的事实是否进入 `legal_fact_map`，并区分事实关联与法律结论；
- 完整提取、跨材料核对、法律事实复核三轮是否分别完成并记录范围；
- 每个结果文件是否能反查原文件名和原路径；
- 所有改名是否符合命名规则，日期来源是否注明；
- 是否在事实提取前检查了全部录音；缺少逐字稿或对应关系不明时是否停止生成报告和时间轴；
- 是否保留原录音，且未安装或调用本地语音识别服务；
- 是否用逐字稿形成候选主线，并完成全部材料的印证、反证、遗漏和缺口检查；
- Word 报告是否只包含案件主体、案件总结、关键时间轴和文件清单四个核心部分；案件总结中是否包含重要事实完整梳理和法律事实及要素对应；
- 案件主体、起因、过程、争议、现状、缺口和主线事件是否均非空；首次缺项是否只补充扫描一次，第二次仍失败时是否如实列出缺口；
- 关键时间轴是否为五列表格，且与独立可视化时间轴事件一致；
- 可视化时间轴是否在 Word 报告成功后生成，且事件快照与报告一致；
- Word 和时间轴是否不包含内部编号、SHA-256、重复组、版本组、原文定位或机器路径；
- 是否先提取候选事实再合并事件，且没有错误合并同日不同事项；
- 主时间轴是否只保留案件主线，工商设立和历史变更是否进入 Word 报告的主体或背景说明；
- 事件发生时间、材料形成时间和文件修改时间是否分开；
- 时间轴是否按日期排序，每条是否显示可读的相关材料名称，并能通过内部 JSON 反查编号和路径；
- `002 基础资料/index.md` 的数量与该目录实际文件数量是否一致；
- 空分类目录是否保留说明文件；
- 执行前 `归档目录预览.md` 是否完整展示改名后的一级、二级目录树；
- 执行后确认 Markdown 是否位于 `整理结果/技术资料`，且 AI 已在对话中直接展示目录树和 A/B/C 选项；
- 完成后是否尝试在访达或文件资源管理器中定位案件根文件夹，并将真实绝对路径裸露、单独成行显示；
- Word 是否可打开，标题、正文和表格是否完整、无截断或空白异常；
- HTML/PNG/PDF 文字是否清晰、节点顺序是否与 Word 报告一致、附件引用是否存在。
- 所有律师可见内容是否遵守 `lawyer-writing.md`，且未出现解析、哈希、置信度、重复组、版本组或内部编号等系统术语。

关键项失败时先修复；无法修复时列出阻塞原因并请求用户确认，不得静默忽略。

快速归档只检查文件是否全部登记和归档，不要求内容覆盖率。案件脉络与正式报告检查关键材料和关键事实追溯；只有全量复核模式才检查全部材料覆盖率、阅读单元覆盖率和三轮复核。任何模式都不得把未执行的阅读范围表述为已完成。
