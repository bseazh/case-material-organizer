# 输出结构与字段

## 结果目录

```text
{序号}-{原告简称}VS{被告简称}-{案由}/
├── 001 主体信息/
├── 002 基础资料/
│   ├── 01 合同协议/
│   ├── 02 付款凭证/
│   ├── 03 履约交付/
│   ├── 04 质量检测报告/
│   └── index.md
├── 003 委托材料/
├── 004 类案及法律检索/
├── 005 法律文书/
└── 整理结果/
    ├── {确认案由}案件梳理报告.docx
    ├── {确认案由}案件关键时间轴.html
    └── 技术资料/
        ├── 归档结果目录.md
        └── 归档方案_已执行.json
```

原始文件夹不放入结果目录，不改变其内容。分类结果默认是副本。

上图是默认模式示意，`002` 的具体二级目录必须根据本案材料内容生成，不要求每案完全相同。用户选择自定义模式时，用已确认的自定义材料目录替换 `001` 至 `005`，`整理结果`结构保持不变。

例如：`1-张三VS李四-买卖合同纠纷`。案件根文件夹名称必须在归档前由用户确认，完成后向用户显示其绝对路径。

## 律师成果

默认只交付两类成果：

1. `{确认案由}案件梳理报告.docx`：案件主体、案件总结、关键时间轴表格、文件清单；
2. `{确认案由}案件关键时间轴.html`。只有用户明确要求时，才额外导出 PNG 或 PDF。

确认案由来自 `cause_of_action_review.primary_cause`。项目文件夹、文件名、Word 主标题、HTML 浏览器标题和页面标题必须使用同一个值。

报告和时间轴面向非技术用户，不得显示材料/事件/主体/问题的内部编号、SHA-256、重复组、版本组、原文定位或机器路径。这些数据仅保留在 `整理结果/技术资料/归档方案_已执行.json` 中。

内部执行 JSON 必须包含 `reading_coverage`、`fact_inventory`、`fact_disposition` 和 `legal_fact_map`。旧版本 JSON 缺少任一字段时，不得直接生成新版正式报告；必须回到原材料补做完整阅读与三轮复核。覆盖率由明细计算，不能只保存或手工修改一个百分比。

## 链路总览要求

总览必须基于合并后的事件，说明“起因—过程—争议—现状—缺口”的整体链路，不得把单文件摘要拼接成结论。总览正文不显示内部编号；需要追溯时使用内部 JSON 和索引。

## 002/index.md

按材料日期升序；日期未知置于末尾。包含：日期、材料名称、相对路径、对应事项，不显示内部材料编号。

## 技术资料/归档结果目录.md

根据已执行方案生成，供 AI 留存确认过程，不作为律师主要成果。包含材料总数、已整理材料、需人工查看和实际目录树。执行前预览仍展示原名与改名结果供用户确认；执行后不显示逐文件映射。
