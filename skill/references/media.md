# 录音、逐字稿与沟通纪要规则

## 前置闸门

清点文件后、提取案件事实前，先运行 `scripts/check_media.py`。发现录音时必须保留录音原件，并检查每个录音是否存在可确认对应的逐字稿。

- 全部录音均有明确逐字稿：进入案件分析；
- 任一录音缺少逐字稿：暂停案件分析，不生成案件主线、报告或时间轴；
- 存在逐字稿但对应关系不明：列出候选关系，等待用户确认后再继续；
- 视频适用相同规则，但不要求 Skill 播放或识别媒体本体。

不得提供“跳过录音并继续形成完整案件结论”的默认选项。用户明确要求先整理其他材料时，只能完成清点、目录预览或归档准备，并注明案件梳理尚未完成。

## 给用户的固定提示

> 发现录音材料。录音可能串联案件事实，正式梳理前需要对应逐字稿。请打开阿里云听悟完成转写：
> https://tingwu.aliyun.com/home
>
> 转写后请将逐字稿放回原材料文件夹，建议与录音使用相同日期和主体名称。完成后回复：
> A. 已补充逐字稿，请重新检查；
> B. 查看缺少逐字稿的录音清单；
> C. 仅保存当前清点结果，暂不形成案件报告。

Skill 不安装 Whisper，不调用本地语音识别服务，不上传录音，也不替用户操作第三方转写网站。

## 可接受逐字稿

TXT、MD、DOCX、PDF 均可；扫描 PDF 需要 OCR。逐字稿必须作为独立文件保存，不能只存在于聊天消息。建议命名：

```text
220509-质量争议沟通录音.m4a
220509-质量争议沟通录音-逐字稿.docx
```

## 匹配顺序

1. 基础文件名完全相同，仅扩展名不同；
2. 基础文件名相同并增加 `-逐字稿`、`_逐字稿`、`-转写原文` 或 `（逐字稿）`；
3. 日期、主体和主题同时一致，且逐字稿正文明确写明对应媒体文件名；
4. 仅日期相同只能列为候选，不得自动确认；
5. 一份逐字稿疑似对应多个录音，或一个录音存在多个逐字稿版本时，交给用户确认并全部保留。

## 逐字稿分析顺序

1. 完整读取逐字稿，不得只读摘要或前几页；
2. 识别发言人、时间锚点、承诺、自认、让步、争议口径和提及的外部材料；
3. 形成“候选案件主线”，不得立即写成已确认事实；
4. 用合同、付款凭证、聊天、检测报告、工商材料及其他文件逐项印证或反证；
5. 对逐字稿提及但卷内缺失的材料，写入“缺口与待补材料”；
6. 对未在逐字稿出现但其他材料能够证明的重要事件，仍应纳入主线；
7. 完成全量材料反向检查后，才生成最终事件表、Word 报告和可视化时间轴。

逐字稿优先用于理解全案，不享有事实上的当然优先效力。日期、主体、金额、数量或责任口径冲突时，应并列来源并标注“待确认”；书面材料也不得未经核验自动优先。

## 沟通纪要

逐字稿内容复杂时，先形成内部沟通纪要，至少整理：基本信息、与会人员、过程时间线、讨论焦点、明确共识、下一步事项、风险与待核事项。关键表述尽量保留 `[HH:MM:SS]` 时间锚点。

沟通纪要是分析中间件，可归档到 `002 基础资料` 的录音或沟通类二级目录，但默认不作为第三份对外成果。最终律师成果仍为案件梳理报告和独立可视化时间轴。

## 证据边界

- 原录音始终保留并归档；
- Skill 不根据录音时长、文件名或转写摘要补造事实；
- 逐字稿不代表录音真实性、完整性或说话人身份已确认；
- 关键金额、承诺、自认和身份表述应提示律师回听原声；
- 报告中使用“逐字稿记载”“某方在会谈中陈述”等限定语。
